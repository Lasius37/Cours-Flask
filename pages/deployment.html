    Comprendre le déploiement

    Pendant le développement, l'application est exécutée sur l'ordinateur du développeur avec une commande comme : 

    flask --app app run --debug

    Le déploiement consiste à installer et exécuter l'application dans un environnement où elle pourra être utilisée par ses utilisateurs.

    Cet environnement peut être :

    • un serveur appartenant à l'organisation
    • un ordinateur accessible sur un réseau local
    • une plateforme d'hébergement
    • un serveur accessible depuis Internet

    Le déploiement ne consiste donc pas uniquement à copier les fichiers du projet. Il faut également :

    • installer Python et les dépendances
    • charger une configuration adaptée
    • préparer la base de données
    • utiliser un serveur adapté à la production
    • prévoir le stockage des fichiers persistants
    • protéger les informations sensibles

    Le serveur lancé avec flask run est uniquement destiné au développement. Il ne doit pas être utilisé pour faire fonctionner une application en production.

    Vérifier le projet

    Avant de préparer le déploiement, l'application doit fonctionner correctement dans son environnement de développement.

    Il faut notamment vérifier :

    • que toutes les pages sont accessibles
    • que les formulaires sont validés correctement
    • que les données peuvent être créées, modifiées et supprimées
    • que les fichiers envoyés sont enregistrés et affichés
    • que les erreurs courantes sont prises en charge
    • que les migrations sont à jour

    La commande suivante permet de vérifier si les modèles contiennent des modifications qui n'ont pas encore été intégrées dans une migration : 

    flask --app app db check

    Si une modification est détectée, il faut créer et appliquer une migration avant le déploiement. 

    flask --app app db migrate -m "Description de la modification"
flask --app app db upgrade

    Préparer les dépendances

    L'environnement de production doit pouvoir installer les mêmes bibliothèques Python que l'environnement de développement. Elles sont enregistrées dans le fichier requirements.txt. 

    pip freeze > requirements.txt

    Ce fichier peut par exemple contenir : 

    Flask==3.1.2
Flask-Migrate==4.1.0
Flask-SQLAlchemy==3.1.1
Flask-WTF==1.2.2
waitress==3.0.2

    Les numéros de version dépendent des bibliothèques installées dans l'environnement virtuel. Dans un nouvel environnement, les dépendances peuvent être installées avec : 

    pip install -r requirements.txt

    Le fichier requirements.txt doit être ajouté au dépôt Git, mais l'environnement virtuel .venv ne doit pas l'être.

    Préparer la configuration

    La configuration utilisée pendant le développement ne doit pas être reprise sans vérification. La configuration propre à l'installation peut être placée dans instance/config.py. Ce fichier peut notamment définir : 

    SECRET_KEY = "une-cle-longue-et-imprevisible"

SQLALCHEMY_DATABASE_URI = "sqlite:///production.db"

MAX_CONTENT_LENGTH = 2 * 1024 * 1024

    La fabrique charge d'abord la configuration générale, puis la configuration propre à l'installation : 

    def create_app():
    app = Flask(
        __name__,
        instance_relative_config=True
    )

    app.config.from_object(Config)

    app.config.from_pyfile(
        "config.py",
        silent=True
    )

    # Suite de l'initialisation

    return app

    Les valeurs de instance/config.py remplacent les valeurs générales portant le même nom.

    Préparer la base de données

    Le code de l'application et le dossier des migrations ne suffisent pas à créer les tables dans un nouvel environnement. Après l'installation du projet, il faut appliquer les migrations : 

    flask --app app db upgrade

    Cette commande :

    • crée les tables qui n'existent pas encore
    • applique les modifications successives des modèles
    • enregistre la version actuelle de la base

    Le dossier migrations doit être présent dans le dépôt Git afin que la structure de la base puisse être reconstruite. Les données de développement ne doivent pas nécessairement être copiées dans la base utilisée après le déploiement. Il faut déterminer séparément :

    • la structure attendue de la base
    • les données initiales réellement nécessaires
    • les données de test qui ne doivent pas être conservées

    Utiliser un serveur de production

    Flask est une application WSGI. En production, elle doit être exécutée par un serveur WSGI adapté. Le serveur Waitress fonctionne sous Windows et ne nécessite pas de compilation particulière. Pour l'installer : 

    pip install waitress

    Mettre ensuite à jour les dépendances : 

    pip freeze > requirements.txt

    Une application utilisant la fabrique create_app() peut être lancée avec : 

    waitress-serve --host 127.0.0.1 --call app:create_app

    L'option --call indique que create_app doit être appelée pour obtenir l'application. L'application est alors accessible localement à l'adresse : 

    http://127.0.0.1:8080
    Élément Rôle
    waitress-serve Lancer le serveur WSGI Waitress
    --host 127.0.0.1 Accepter uniquement les connexions provenant de l'ordinateur local
    --call Appeler la fabrique d'application
    app:create_app Charger la fonction create_app du package app

    Le serveur Waitress ne doit pas être lancé avec l'option de débogage. Les erreurs détaillées ne doivent pas être affichées aux utilisateurs.

    Prévoir le stockage des fichiers

    Certaines données doivent rester disponibles après l'arrêt ou la mise à jour de l'application. C'est notamment le cas :

    • de la base de données
    • des fichiers envoyés par les utilisateurs
    • de la configuration propre à l'installation
    instance/
    ├── config.py
    ├── production.db
    └── uploads/

    Ces fichiers sont appelés données persistantes. Ils doivent être conservés indépendamment du code de l'application.

    Certains environnements d'hébergement réinitialisent les fichiers locaux lors d'une mise à jour ou d'un redémarrage. Il faut vérifier que la base et les fichiers envoyés sont enregistrés dans un emplacement persistant. Une sauvegarde régulière doit également être prévue pour les données importantes.

    Gérer les erreurs

    En production, une erreur ne doit pas afficher le détail du code Python à l'utilisateur. Flask affiche par défaut une page simple pour une erreur interne lorsque le mode de débogage n'est pas activé. Une page personnalisée peut être créée pour les erreurs les plus fréquentes. 

    from flask import render_template


def register_error_handlers(app):

    @app.errorhandler(404)
    def page_not_found(error):
        return render_template(
            "errors/404.html"
        ), 404

    @app.errorhandler(500)
    def internal_error(error):
        return render_template(
            "errors/500.html"
        ), 500

    La fonction est ensuite appelée dans la fabrique : 

    register_error_handlers(app)

    Les erreurs techniques doivent être enregistrées dans les journaux du serveur afin de pouvoir être analysées sans être présentées aux utilisateurs.

    Préparer le dépôt Git

    Le dépôt doit contenir tout ce qui est nécessaire pour reconstruire l'application. Il doit notamment contenir :

    • le code Python
    • les templates
    • les fichiers statiques
    • le dossier des migrations
    • le fichier requirements.txt

    Il ne doit pas contenir :

    • l'environnement virtuel
    • les fichiers temporaires de Python
    • la base de données locale
    • les fichiers envoyés par les utilisateurs
    • la configuration contenant les secrets

    Le fichier .gitignore peut par exemple contenir : 

    .venv/
__pycache__/
instance/

    Le dossier migrations ne doit pas être ignoré. Il appartient au code du projet et permet de reconstruire la structure de la base.

    Utiliser une liste de contrôle

    Avant chaque déploiement, les vérifications suivantes peuvent être effectuées.

    Vérification État attendu
    L'application fonctionne localement Aucune erreur bloquante
    Les dépendances sont enregistrées requirements.txt est à jour
    Les migrations sont créées flask db check ne détecte aucune modification
    La configuration locale est protégée Les secrets ne sont pas dans Git
    Le serveur de production est installé Waitress peut lancer l'application
    Les données persistantes sont identifiées La base et les fichiers seront conservés
    Le mode de débogage est désactivé Les erreurs détaillées ne sont pas affichées
    Le dépôt Git est propre Aucun secret ou fichier local n'est publié

    Erreurs fréquentes

    • Utiliser flask run en production : le serveur de développement n'est pas conçu pour cet usage .
    • Activer le mode de débogage : des informations techniques sensibles peuvent être affichées .
    • Oublier d'ajouter Waitress aux dépendances : le serveur ne peut pas être installé dans le nouvel environnement .
    • Ne pas appliquer les migrations : la structure de la base ne correspond pas aux modèles .
    • Publier la clé secrète : les données signées par l'application peuvent être compromises .
    • Copier l'environnement virtuel : il peut contenir des chemins et des fichiers propres à l'ordinateur de développement .
    • Oublier les fichiers envoyés par les utilisateurs : les noms enregistrés dans la base peuvent pointer vers des fichiers absents .
    • Stocker la base dans un emplacement temporaire : les données peuvent disparaître après un redémarrage .
    • Ignorer le dossier migrations dans Git : la structure de la base ne peut pas être reconstruite correctement .
    • Ne pas prévoir de sauvegarde : une panne ou une erreur peut entraîner une perte définitive des données .
