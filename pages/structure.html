    Organiser le projet

    L'application peut être placée dans un package principal nommé app. Chaque grande fonctionnalité peut ensuite être placée dans son propre sous-package. Par exemple : 

    project/
│
├── app/
│   ├── __init__.py
│   ├── extensions.py
│   ├── models.py
│   │
│   ├── main/
│   │   ├── __init__.py
│   │   └── routes.py
│   │
│   ├── first_functionality/
│   │   ├── __init__.py
│   │   ├── routes.py
│   │   └── templates/
│   │       └── first_functionality/
│   │           ├── list.html
│   │           ├── detail.html
│   │           ├── create.html
│   │           └── update.html
│   │
│   ├── second_functionality/
│   │   ├── __init__.py
│   │   ├── routes.py
│   │   └── templates/
│   │       └── second_functionality/
│   │           ├── list.html
│   │           ├── detail.html
│   │           ├── create.html
│   │           └── update.html
│   │
│   ├── static/
│   │   ├── css/
│   │   ├── js/
│   │   └── images/
│   │
│   └── templates/
│       └── base.html
│
├── instance/
│   └── database.db
│
├── run.py
└── requirements.txt

    Chaque fichier ou dossier possède une responsabilité précise :

    Élément Rôle
    app/__init__.py Créer et configurer l'application
    app/extensions.py Créer les extensions utilisées par l'application
    app/models.py Contenir les modèles de la base de données
    app/main Contenir les routes générales de l'application (ex : accueil, ...)
    app/first_functionality Contenir les routes consacrées à la première fonctionnalité
    app/second_functionality Contenir les routes consacrées à la deuxième fonctionnalité
    app/templates Contenir les templates communs
    app/static Contenir les fichiers statiques communs
    run.py Créer l'application et lancer le serveur

    Les fichiers __init__.py indiquent que les dossiers concernés sont des packages Python.

    Le package main contient lui aussi un blueprint. Il rergoupe les pages générales de l'application, comme l'accueil. Sa création et son enregistrement suivent les mêmes principes que les autres fonctionnalités plus spécifiques.

    Créer une fabrique d'application

    Jusqu'à présent, l'application était généralement créée directement : 

    app = Flask(__name__)

    Dans une application structurée, cette création est placée dans une fonction.

    Cette fonction est appelée une fabrique d'application, ou application factory.

    Dans le fichier app/__init__.py : 

    from flask import Flask

def create_app():
    app = Flask(__name__)

    return app

    La fonction create_app() permet de :

    • créer l'application
    • charger sa configuration
    • initialiser les extensions
    • enregistrer les blueprints
    • renvoyer l'application prête à être utilisée

    Cette organisation évite de dépendre d'une unique application créée automatiquement au moment des imports.

    Séparer les extensions

    Les extensions utilisées par l'application peuvent être créées dans un fichier séparé.

    Dans app/extensions.py : 

    from flask_sqlalchemy import SQLAlchemy

db = SQLAlchemy()

    L'objet db est créé sans être immédiatement associé à une application.

    Il est ensuite initialisé dans la fabrique : 

    from flask import Flask

from .extensions import db

def create_app():
    app = Flask(__name__)

    app.config["SQLALCHEMY_DATABASE_URI"] = \
        "sqlite:///database.db"

    db.init_app(app)

    return app

    La méthode init_app() associe l'extension à l'application créée par create_app().

    Cette méthode permet à plusieurs modules d'importer le même objet db sans recréer SQLAlchemy.

    Créer un blueprint

    Un blueprint est un ensemble de routes regroupées autour d'une fonctionnalité.

    Il ne constitue pas une application Flask autonome. Il doit être enregistré dans une application pour que ses routes deviennent disponibles.

    Le blueprint consacré à une fonctionnalité peut être créé dans : 

    app/my_functionality/__init__.py
    from flask import Blueprint

my_functionality_bp = Blueprint(
    "my_functionality",
    __name__,
    template_folder="templates"
)

    Le premier argument correspond au nom interne du blueprint : 

    "my_functionality"

    Ce nom sera notamment utilisé dans url_for().

    L'argument __name__ permet à Flask de repérer les ressources associées au blueprint.

    L'argument template_folder indique le dossier contenant ses templates.

    On procède de même pour chaque fonctionnalité afin de séparer clairement les différentes parties de l'application.

    Associer des routes au blueprint

    Les routes consacrées à cette fonctionnalité sont placées dans : 

    app/my_functionality/routes.py

    Le blueprint est importé depuis le package actuel : 

    from flask import render_template

from . import my_functionality_bp

@my_functionality_bp.route("/")
def my_view():
    return render_template(
        "my_functionality/my_template.html"
    )

    La route est associée à my_functionality_bp et non directement à l'application.

    Il faut ensuite importer le fichier contenant les routes à la fin du fichier app/my_functionality/__init__.py : 

    from . import routes

    Cet import permet d'exécuter les décorateurs présents dans routes.py et donc d'associer les routes au blueprint. Il est placé après la création du blueprint afin d'éviter un import circulaire.

    Enregistrer un blueprint

    Le blueprint doit être enregistré dans la fabrique d'application.

    Dans app/__init__.py : 

    from flask import Flask

from .extensions import db

def create_app():
    app = Flask(__name__)

    app.config["SQLALCHEMY_DATABASE_URI"] = \
        "sqlite:///database.db"

    db.init_app(app)

    from .my_functionality import my_functionality_bp

    app.register_blueprint(
        my_functionality_bp,
        url_prefix="/my_functionality"
    )

    return app

    Le paramètre url_prefix ajoute un préfixe commun à toutes les routes du blueprint. Avec le préfixe suivant : 

    url_prefix="/my_functionality"

    la route "/" définie dans le blueprint devient : 

    /my_functionality/

    Une autre route définie ainsi : 

    @my_functionality_bp.route("/create")

    devient : 

    /my_functionality/create

    Organiser les templates

    Les templates propres à un blueprint peuvent être placés dans son package. 

    app/
└── my_functionality/
    └── templates/
        └── my_functionality/
            ├── list.html
            ├── detail.html
            ├── create.html
            └── update.html

    Le second dossier my_functionality évite les conflits entre des templates portant le même nom.

    Par exemple, plusieurs blueprints pourraient contenir un fichier detail.html.

    Pour afficher le bon template : 

    return render_template(
    "my_functionality/detail.html"
)

    Le template commun base.html peut rester dans le dossier principal : 

    app/templates/base.html

    Les templates du blueprint peuvent alors en hériter normalement : 

    {% extends "base.html" %}

    Adapter les liens

    Lorsqu'une fonction de vue appartient à un blueprint, son nom complet contient :

    • le nom du blueprint
    • le nom de la fonction de vue

    Ces deux éléments sont séparés par un point : 

    my_functionality.my_view

    Un lien vers ce template s'écrit donc : 

    <a href="{{ url_for('my_functionality.my_view') }}">
    Lien
</a>

    Pour une route dynamique : 

    @my_functionality_bp.route(
    "/<int:my_id>"
)
def my_view(my_id):
    pass

    le lien devient : 

    <a href="{{ url_for(
    'my_functionality.my_view',
    my_id=my.id
) }}">
    Afficher
</a>

    Séparer les modèles

    Les modèles peuvent être placés dans le fichier app/models.py. 

    from .extensions import db

class MyModel(db.Model):
    id = db.Column(
        db.Integer,
        primary_key=True
    )

    name = db.Column(
        db.String(150),
        nullable=False
    )

    Le point placé devant extensions correspond à un import relatif.

    Il indique que le fichier extensions.py se trouve dans le même package que models.py.

    Les fonctions de vue peuvent ensuite importer les modèles : 

    from ..models import MyModel

    Les deux points indiquent qu'il faut remonter du package my_functionality vers le package app.

    Les modèles doivent être importés avant l'appel à db.create_all(). 

    with app.app_context():
    from . import models

    db.create_all()

    Lancer l'application

    Le fichier run.py est placé à la racine du projet. Il importe la fabrique et crée l'application : 

    from app import create_app

app = create_app()

if __name__ == "__main__":
    app.run(
        debug=True
    )

    L'application peut ensuite être lancée depuis la racine du projet : 

    python run.py

    Python importe la fonction create_app() depuis le fichier app/__init__.py.

    Erreurs fréquentes

    • Oublier un fichier __init__.py : le package n'est pas organisé comme prévu.
    • Créer plusieurs objets db : les modèles et l'application n'utilisent pas la même instance de SQLAlchemy.
    • Oublier db.init_app(app) : SQLAlchemy n'est pas associé à l'application.
    • Définir une route avec @app.route dans un blueprint :le fichier ne possède pas directement l'application .
    • Oublier d'importer routes dans le fichier __init__.py du blueprint : les routes ne sont pas associées au blueprint.
    • Oublier d'enregistrer un blueprint : ses routes n'existent pas dans l'application.
    • Oublier le nom du blueprint dans url_for() : Flask ne trouve pas la fonction de vue demandée.
    • Utiliser un mauvais chemin de template : une erreur TemplateNotFound apparaît.
    • Importer les modules dans un ordre incorrect : un import circulaire peut apparaître.
    • Lancer run.py depuis un mauvais dossier : Python ne trouve pas le package app.
